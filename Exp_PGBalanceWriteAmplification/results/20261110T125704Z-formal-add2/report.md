# PG 均衡写放大：8 → 10 OSD 实测（新增 2 个）

运行时间（北京时间）：2026-11-10T20:57:04+08:00。

客户端写入 17,179,869,184 B（16.000 GiB），4096 个 4 MiB 对象；三副本、128 PG、并发 32。

测试池全程使用独立的 osd 故障域规则；按池 flat 权重先将 node3 权重设为 0，预先将未加入的 node3 叶子 OSD 权重设为 0，随后在一个 CRUSH 更新中将 node3 桶权重恢复为所选 2 个 OSD 的权重之和。新增 OSD ID 为 [8, 9]。12 个 OSD 全程 up/in，既有 .mgr 池继续使用原 host 规则。未停止守护进程，也未更改副本数。

关闭测试池压缩、PG 自动调整和 scrub；临时暂停自动 balancer。只有初始装载向测试池写数据，均衡和空闲窗口不提交客户端测试写入。

**主指标**：全部 OSD Messenger worker 的 msgr_recv_bytes 增量之和 / (3 × 客户端成功提交字节数)。这些是消息接收字节，包含消息头、元数据、心跳等，所以是纯数据接收放大的近似，不能称为精确的 payload 或 SSD 物理写放大。RDMA rx_bytes 是另一层诊断计数，没有与 Messenger 字节相加。

- 初始装载接收放大：**1.000469×**。
- 装载加均衡累计接收放大：**1.199798×**。
- 均衡新增放大：**0.199328**，即正常三副本数据量的 19.933%。
- 相对实测初始装载接收量，累计增幅：**19.923%**。
- BlueStore write_big_bytes + write_small_bytes 交叉核对：初始 1.000000×，累计 1.198735×。这统计全部 OSD 数据写入路径处理的字节，包括内部对象写入，不能按池过滤；既不是接收计数，也不含完整设备内部写入。

均衡接收量是随后匹配空闲窗口的 394.8 倍；按空闲接收速率折算的背景估计为 25,846,040 B。主结果保留原始增量，没有扣背景。

初始和最终映射中，68 个 PG 的副本 OSD 集合发生变化，共新增 75 个 PG 副本位置。按每 PG 的已存对象字节计算，必要新增副本数据为 10,242,490,368 B，其中 node3 为 10,053,746,688 B；由实际映射推导的归一化值为 1.198730×。它是映射和对象大小推导，需与实际数据路径计数分别看待。

细分迁移量：node3 接收 9.363281 GiB，原有 8 个 OSD 之间另外迁移 0.175781 GiB，合计 9.539062 GiB。实测 push_out_bytes 与该推导量之差为 0 B。均匀分布理论值为 9.600000 GiB、1.200000×；实际 PG 分布和旧 OSD 间迁移会使结果偏离该值。

node3 均衡窗口 Messenger 接收 10,065,155,463 B，BlueStore stored 增加 10,053,819,492 B。

均衡后完整读回并逐字节核对全部 4096 个对象，合计 17,179,869,184 B。验证和删除测试数据均在测量窗口外。

初始和最终 pool 统计保留在 results.json；用于检查对象数、三副本数、客户端累计写入量及无 clone。逻辑对象字节使用详细 PG 的 stat_sum.num_bytes，不把 librados 池汇总中的 raw/allocated num_bytes 当作逻辑数据量。原始完整 perf 快照在 raw-counters.json.gz；per-osd.csv 可查看迁移来源和目标的分项，pg-movement.csv 可核对每 PG 映射。

本次是单次原理验证，没有重复实验的置信区间。均匀分布估计不代替实际 PG 映射；三副本期间发生额外旧 OSD 间迁移时，实际值可以高于理论估计。
