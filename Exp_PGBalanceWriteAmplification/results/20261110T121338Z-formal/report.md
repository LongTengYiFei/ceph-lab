# PG 均衡写放大：8 → 12 OSD 实测

运行时间（北京时间）：2026-11-10T20:13:38+08:00。

客户端写入 17,179,869,184 B（16.000 GiB），4096 个 4 MiB 对象；三副本、128 PG、并发 32。

测试池全程使用独立的 osd 故障域规则；按池 flat 权重先将 node3 权重设为 0，随后在一个 CRUSH 更新中恢复其原始权重。12 个 OSD 全程 up/in，既有 .mgr 池继续使用原 host 规则。未停止守护进程，也未更改副本数。

关闭测试池压缩、PG 自动调整和 scrub；临时暂停自动 balancer。只有初始装载向测试池写数据，均衡和空闲窗口不提交客户端测试写入。

**主指标**：全部 OSD Messenger worker 的 msgr_recv_bytes 增量之和 / (3 × 客户端成功提交字节数)。这些是消息接收字节，包含消息头、元数据、心跳等，所以是纯数据接收放大的近似，不能称为精确的 payload 或 SSD 物理写放大。RDMA rx_bytes 是另一层诊断计数，没有与 Messenger 字节相加。

| 阶段 | 客户端测试写入 B | Messenger 接收 B | BlueStore 数据写入 B | push_out_bytes | 秒 |
|---|---:|---:|---:|---:|---:|
| 8 OSD 空闲 | 0 | 4,730,160 | 0 | 0 | 15.361 |
| 初始装载 | 17,179,869,184 | 51,563,485,128 | 51,539,607,552 | 0 | 16.728 |
| 8→12 均衡 | 0 | 18,497,625,847 | 18,451,001,212 | 18,450,743,296 | 107.983 |
| 12 OSD 匹配空闲 | 0 | 37,794,308 | 0 | 0 | 108.509 |

- 初始装载接收放大：**1.000463×**。
- 装载加均衡累计接收放大：**1.359364×**。
- 均衡新增放大：**0.358901**，即正常三副本数据量的 35.890%。
- 相对实测初始装载接收量，累计增幅：**35.873%**。
- BlueStore write_big_bytes + write_small_bytes 交叉核对：初始 1.000000×，累计 1.357997×。这统计数据写入路径处理的字节，既不是接收计数，也不含完整设备内部写入。

均衡接收量是随后匹配空闲窗口的 489.4 倍；按空闲接收速率折算的背景估计为 37,610,961 B。主结果保留原始增量，没有扣背景。

初始和最终映射中，93 个 PG 的副本 OSD 集合发生变化，共新增 136 个 PG 副本位置。按每 PG 的已存对象字节计算，必要新增副本数据为 18,450,743,296 B，其中 node3 为 17,771,266,048 B；由实际映射推导的归一化值为 1.357992×。它是映射和对象大小推导，需与实际数据路径计数分别看待。

细分迁移量：node3 接收 16.550781 GiB，原有 8 个 OSD 之间另外迁移 0.632812 GiB，合计 17.183594 GiB。实测 push_out_bytes 与该推导量之差为 0 B。实际 PG 分布和旧 OSD 间迁移解释了与均匀分布 4/3 估计的差别。

node3 均衡窗口 Messenger 接收 17,789,868,715 B，BlueStore stored 增加 17,771,340,916 B。

均衡后完整读回并逐字节核对全部 4096 个对象，合计 17,179,869,184 B。验证和删除测试数据均在测量窗口外。

初始和最终 pool 统计保留在 results.json；用于检查对象数、三副本数、客户端累计写入量及无 clone。逻辑对象字节使用详细 PG 的 stat_sum.num_bytes，不把 librados 池汇总中的 raw/allocated num_bytes 当作逻辑数据量。原始完整 perf 快照在 raw-counters.json.gz；per-osd.csv 可查看迁移来源和目标的分项，pg-movement.csv 可核对每 PG 映射。

本次是单次原理验证，没有重复实验的置信区间。均匀分布下的 4/3 估计不代替实际 PG 映射；三副本期间发生额外旧 OSD 间迁移时，实际值可以高于 4/3。
