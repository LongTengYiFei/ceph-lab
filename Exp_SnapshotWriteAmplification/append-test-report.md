# Ceph 17.2.7 大对象追加与周期快照：元数据逻辑写放大测试报告

## 1. 主要结果

在 1,024 个初始大小为 16 MiB 的对象上，每轮向每个对象追加 512 KiB，共追加十轮。
快照组在初始装载后和每轮追加后各创建一次 pool 快照，共保留 S0–S10 十一个快照；
对照组执行相同写入，不创建快照。两组串行运行，分别重置计数器。

**十轮追加期间，有快照组向 RocksDB 提交 578,733,328 B，无快照组提交
162,447,122 B，前者为后者的 3.56260 倍，额外提交 416,286,206 B。**
平均到每个对象的每次追加，有快照组提交 56.52 KB，无快照组提交 15.86 KB，
快照额外增加约 **40.65 KB**。两组所有追加窗口的 deferred 写入字节增量均为 0。

源码分析确认，快照追加引入旧版本 clone 的对象信息和完整块映射、映射内的校验和、
共享块引用计数、SnapSet、快照索引以及额外 PG 日志。
**本次已经测得总提交量，但没有测得这些类别各自的提交字节占比。**
下文将实测结果与源码推导分别说明。

## 3. 统计口径与阶段定义

计数位于 `RocksDBStore::submit_common()`，累计全部 12 个 OSD **成功提交给 RocksDB
的序列化 WriteBatch 字节数**。同步和异步提交路径均覆盖，包含 key、value、操作编码、
每批次 12 B 固定头以及空批次；失败提交不计入。

因此，本报告衡量的是 **OSD 向 RocksDB 提交的逻辑字节量**，不包含 RocksDB 内部
WAL、SST flush 和 compaction 的物理输出，也不代表 SSD 的物理写放大。
计数器没有按 pool 分类，采用串行测试；每阶段等待计数收敛后取差值。

| 统计阶段 | 包含的操作 |
|---|---|
| 初始装载 | 将 1,024 个 16 MiB 对象写入测试池 |
| 十轮追加 | 十次追加窗口，包括追加触发的 clone、共享引用和其他元数据操作 |
| 创建快照 | 单独执行 S0–S10 创建操作的十一个窗口 |
| 对应空闲窗口 | 无快照组在对应位置执行的空闲对照 |
| 全流程 | 初始装载、十轮追加以及快照创建或对应空闲窗口的累计 |

全流程不包含建池、读回校验和删除测试池。
本报告的 KB、MB 分别为 1,000 B、1,000,000 B；KiB、MiB、GiB 按二进制计算。

另行记录 `bluestore.issued_deferred_write_bytes` 的增量，作为 deferred 数据进入
数据库路径的辅助诊断。该诊断量没有直接从 `submitted_bytes` 中扣除。

## 4. 定量结果

### 4.1 分阶段累计提交量

| 阶段 | 无快照提交 B | 有快照提交 B | 有/无 |
|---|---:|---:|---:|
| 初始装载 | 23,481,514 | 23,481,347 | 约 1.00 |
| 十轮追加 | 162,447,122 | 578,733,328 | **3.56260** |
| 创建快照 | 0 | 1,151,496 | — |
| 对应空闲窗口 | 0 | 0 | — |
| **全流程** | **185,928,636** | **603,366,171** | **3.24515** |

“十轮追加”的 3.56260 倍衡量在追加期间保留快照产生的提交量变化。
“全流程”的 3.24515 倍还计入两组几乎相同的初始装载成本，以及创建快照的开销。
创建快照本身有数据库提交，已单独计数并包含在全流程中。

追加阶段的额外提交量为：

```text
578,733,328 − 162,447,122 = 416,286,206 B
```

该额外量相当于 5 GiB 客户端追加数据的 **7.7539%**。
这与“有/无快照提交量之比”采用不同分母，应分别理解。

### 4.2 每对象每次追加的平均值

十轮共执行 `1,024 × 10 = 10,240` 次对象追加，按累计提交量除以追加次数：

| 项目 | 平均提交 B/对象/次 | 平均提交 KB/对象/次 |
|---|---:|---:|
| 有快照 | 56,516.93 | 56.52 |
| 无快照 | 15,863.98 | 15.86 |
| **快照额外增加** | **40,652.95** | **40.65** |

这是累计逻辑提交字节的平均值，不是每个对象最终多占用的元数据空间。
同一条元数据在不同事务中反复更新，会被重复计入；各轮实际提交量也并不相同。

## 5. 定性分析：快照额外提交了什么

本节整理已有源码分析，不给出未经分类计数验证的精确字节占比。

### 5.1 新增旧版本 clone 及完整块映射

在已有快照需要保留旧版本时，`PrimaryLogPG::make_writeable()` 触发 clone，
经 `_make_clone()`、`BlueStore::_clone()` 进入 `ExtentMap::dup()`。
新 clone 具有自己的对象信息和块映射，相关 onode 与 extent-map shards 写入
RocksDB 的 `O` 前缀。

因此，即使本轮只追加 512 KiB，新 clone 仍需要描述整个旧对象已有的数据范围。
共享数据块可以避免复制原始数据，但不等于新 clone 不需要保存自己的映射信息。

### 5.2 块映射内还包含 blob 信息和校验和

`Blob::dup()` 复制 `bluestore_blob_t`；`ExtentMap::encode_some()` 在编码映射时
调用 blob 编码，包含物理 extent、共享 ID 和 `csum_data` 等字段。
原始数据块被多个版本共享时，这些序列化的 blob 元数据仍可能在各版本映射中重复保存。

现有 perf 增量显示，初始装载共创建 262,144 个 blob，即每对象 256 个；每轮追加
共创建 8,192 个，即每对象 8 个，均对应 64 KiB/blob。
第 r 轮创建旧版本 clone 时，涉及的 blob 数为：

```text
256 + 8 × (r − 1)
```

因此，首轮涉及 256 个，第十轮涉及 328 个，十轮平均每个 clone 涉及 292 个。

按本次源码路径与参数，使用 CRC32C、4 KiB 校验粒度，每项校验和占 4 B，且测试未设置
改变校验粒度的 alloc hint。由此推导，新 clone 中校验和内容的规模为：

| 项目 | 校验和内容 B/clone |
|---|---:|
| 第一轮：旧对象 16 MiB | 16,384 |
| 第十轮：旧对象 20.5 MiB | 20,992 |
| 十轮平均 | **18,688** |

十轮所有新 clone 的校验和内容合计推导为 **191,365,120 B**。
该数仅表示源码和参数推导的组成项，未包含外层编码、映射和 key，
不是分类计数实测结果，也不据此给出其在额外提交量中的精确占比。

### 5.3 共享数据块引用计数反复更新

`ExtentMap::dup()` 对被 clone 引用的 blob 增加物理范围的共享引用计数，并调用
`write_shared_blob()` 登记更新；`_txc_write_nodes()` 将共享引用映射写入 `X` 前缀。
即使某个 blob 在上一轮已经共享，下一轮增加 clone 时仍需要增加并提交引用计数。

按本次固定负载推导，十轮共涉及 **2,990,080 次**共享 blob 的事务内登记/更新。
这是路径推导数量，不能当作已经测得的独立 KV 分类操作数。
本次实测的全部 KV 操作数差额为 **3,580,407 次**，其中包含上述引用更新及其他操作。

首次 clone 还会把原有 256 个 blob 转为共享，使 head 的相关映射变脏；后续轮次通常
只需把上一轮新增加的 8 个 blob 转为共享，但仍需更新所有被 clone 引用的共享计数。
这为第一轮较高的额外提交量提供了源码层面的解释。

### 5.4 SnapSet 关系、快照索引与 PG 日志

`make_writeable()` 更新 head 的 `clones`、`clone_size`、`clone_snaps` 和
`clone_overlap`；`finish_ctx()` 将整个 SnapSet 编码到 head 的 `snapset` 属性，
随 onode 提交。

在本次每个 clone 对应一个快照、重叠范围为一个区间的条件下，按 `SnapSet::encode()`
推导，每增加一个 clone，关系内容增长 72 B：

| 字段 | 增长 B/clone |
|---|---:|
| clone ID | 8 |
| 重叠映射 | 28 |
| 大小映射 | 16 |
| 快照归属映射 | 20 |
| **合计** | **72** |

第 r 轮 head 比无快照多 `72 × r` B 的 SnapSet 内容，第十轮为 720 B；
十轮平均为 396 B/对象/次，全体对象合计推导为 4,055,040 B。
该关系表的规模不足以单独解释平均额外约 40.65 KB 的总提交量；还需考虑完整映射、
校验和、共享引用以及其他提交。

此外，`PG::update_snap_map()` 经 `SnapMapper::add_oid()` 写入 `OBJ_` 和 `SNA_`
两种 omap 索引；创建 clone 时还会额外生成 `CLONE` 类型 PG 日志。
这些记录也属于快照机制引入的提交内容。

### 5.5 extent-map 重新分片与逐轮波动

`ExtentMap::update()` 检查映射的编码大小；需要重新分片时，`reshard()` 删除旧分片
key 并提交新分片。本版本 `request_reshard()` 的 begin 从清零值取更小值，
能将尾部请求扩展到偏移 0，追加因而也可能引起大范围映射重写。

实测无快照组奇数轮没有重新分片，偶数轮每对象一次；快照组每轮还涉及新 clone
的映射处理，奇数轮共 1,024 次、偶数轮共 2,048 次。
较高提交量与重新分片增量同步，说明映射重写与逐轮波动有关。
现有计数不足以进一步把每个峰值精确拆成各类字节，不能只按快照数量解释波动。

### 5.6 创建快照动作本身也有提交

创建 pool 快照会在 MON 更新 pool/OSDMap 状态，OSD 也会持久化接收到的 map。
因此，创建快照动作本身有元数据及内部状态的持久化开销。
本次将其作为独立阶段记录，避免与后续追加触发的 clone 开销混在同一个窗口。
报告中的 1.15 MB 是 OSD 侧该阶段的总提交量，并非整个集群所有进程的快照元数据量。

## 6. 校验与结果适用范围

- 两组全部 1,024 个 head 对象的最终大小均为 21 MiB；每组抽样 3 个对象完整核对内容。
- 快照组对全部 11 个快照逐个抽样 3 个对象，完整核对对应历史内容，均通过。
- 原始计数覆盖全部 12 个 OSD，测量期间 OSD 进程未重启。
- 测试池已删除，临时单副本许可配置及 scrub 标志已恢复。
- 测试开始和结束均为 `HEALTH_WARN`；`MON_DISK_LOW` 为运行前已有告警。

本次只有一组成对结果，没有重复实验的置信区间。结果适用于本次单副本、无压缩、
64 KiB blob、对齐大块追加和每轮创建快照的负载，不能直接推广到覆盖写、小文件、
不同副本数或不同快照频率。

追加阶段 deferred 增量为 0，支持使用本次提交量对比元数据逻辑输入开销；
计数仍包含 key、编码、批次头和 OSD 内部操作。现有总计数不能反推出各类元数据
精确占比，源码推导也不能替代分类实测。创建快照阶段含内部 deferred 数据，
全流程结果应表述为 RocksDB 逻辑提交量的比较。
